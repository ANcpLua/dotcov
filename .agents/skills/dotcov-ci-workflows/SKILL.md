# DotCov CI workflows

1. Establish ownership before editing. Read the affected workflow and
   [Fallout commands](../../../src/DotCov.Fallout/AGENTS.md).
   [nuget-publish.yml](../../../.github/workflows/nuget-publish.yml) is maintained
   here; it is not generated by Fallout.
   [auto-merge.yml](../../../.github/workflows/auto-merge.yml) is synchronized
   from `ANcpLua/github-settings-automation`: change its owning template for a
   durable update, rather than a local copy that the next sync replaces.
2. Trace each affected event through job conditions and dependencies. Preserve
   the distinction between PR/main validation and release-triggered packing
   and publication. DotCov's Linux/Windows test matrix applies to ordinary CI;
   Fallout upstream's release-only cross-platform policy does not apply here.
3. Preserve the observable contracts:
   - Publication depends on build, tests, and both package groups. Keep the
     `nuget` environment and trusted-publishing authentication intact.
   - Native RID packages and the portable fallback must exist before the
     `DotCov.Tool` pointer is pushed. Keep pointer publication last.
   - Coverage uses the shared project settings described in the
     [test guide](../../../tests/CLAUDE.md). Consume reports from the intended
     run only; missing measurements cannot produce a passing badge or gate.
   - Badge writes remain restricted to Ubuntu pushes to `main`. Preserve
     same-repository checks before privileged auto-merge or branch deletion;
     a branch prefix alone does not establish trust.
4. Validate affected local behavior through the documented Fallout targets.
   Inspect trigger, dependency, and permission changes separately: local tests
   do not exercise GitHub event handling. Report untested event paths explicitly.

Keep this a workflow edit, not a release: tag pushes and manual release dispatches
require a publication request. Avoid cancelling publication partway through.
