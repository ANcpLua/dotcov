# DotCov CI workflows

1. Establish ownership before editing. Read the affected workflow and
   [Fallout commands](../../../src/DotCov.Fallout/AGENTS.md).
   [nuget-publish.yml](../../../.github/workflows/nuget-publish.yml) is maintained
   here; it is not generated by Fallout.
   [dependabot.yml](../../../.github/dependabot.yml) and
   [dependabot-auto-merge.yml](../../../.github/workflows/dependabot-auto-merge.yml)
   are maintained here too, as is the composite
   [badge action](../../../.github/actions/badge/action.yml) and its `badge.sh`,
   which remains available to consumers and `BadgeActionTests` runs against a
   local origin. Auto-merge waits for main's required status checks, so renaming a CI
   job means updating those checks in branch protection.
2. Trace each affected event through job conditions and dependencies. Preserve
   the distinction between PR/main validation and release-triggered packing
   and publication. DotCov's Linux/Windows test matrix applies to ordinary CI;
   Fallout upstream's release-only cross-platform policy does not apply here.
   The `badge-action` Linux/Windows/macOS matrix invokes the composite action with
   its default tool installation against a local bare origin; preserve that isolation
   and its publication dependency so validation never recreates GitHub's `badges` branch.
3. Preserve the observable contracts:
   - Publication depends on build, tests, and both package groups. Keep the
     `nuget` environment and trusted-publishing authentication intact.
   - Native RID packages and the portable fallback must exist before the
     `DotCov.Tool` pointer is pushed. Keep pointer publication last.
   - Coverage uses the shared project settings described in the
     [test guide](../../../tests/CLAUDE.md). Consume reports from the intended
     run only; missing measurements cannot produce a passing badge or gate.
   - The coverage gate (`fallout Coverage --reports TestResults`) rejects
     missing src projects and coverage below the thresholds in `build/Build.cs`.
     This repository does not publish a badge branch; do not add badge pushes
     or write permissions to its test job. The reusable badge action remains
     available for consumers who choose to publish in their own repositories.
     Preserve same-repository checks before privileged auto-merge or branch
     deletion; a branch prefix alone does not establish trust.
4. Run `actionlint` and `shellcheck .github/actions/badge/badge.sh`; the
   `build` job runs both and fails on any finding. Validate affected local
   behavior through the documented Fallout targets.
   Inspect trigger, dependency, and permission changes separately: local tests
   do not exercise GitHub event handling. Report untested event paths explicitly.

Keep this a workflow edit, not a release: tag pushes and manual release dispatches
require a publication request. Avoid cancelling publication partway through.
